Why it is idempotent

Idempotent means: doing it once and doing it five times give the same result. Press the lift button five times — the lift still comes once. This page shows every kind of duplicate this system actually receives, and the specific thing that absorbs it.

Why this is not optional

Pub/Sub, the queue that carries upload notifications, guarantees at-least-once delivery. Not exactly-once. In practice that means:

  • a message can arrive twice, sometimes simultaneously on two workers;
  • messages can arrive out of order, so an old version's event can land after a new one's;
  • a worker that crashes after doing half the work will see the message again.

On top of that, humans create duplicates: they upload the same file twice, they re-upload a file that hasn't actually changed, and a second pipeline (the teaching notebooks) writes the same chunks through a different route. A pipeline that is not idempotent turns each of these into a corrupted index.

The foundation: the key is made from the content

This one decision carries most of the weight.

doc_key = f"{tenant_id}_{sha256_of(bytes)}"

The obvious alternative is to deduplicate on the Pub/Sub message id. It does not work. A message id is stable across a redelivery — so it would catch a retry — but the same PDF uploaded twice is two different messages with two different ids. That is the duplicate users actually create, and the message id misses it entirely.

A content hash catches both. And because Firestore treats a write to an existing id as an update rather than an insert, landing on the same id is exactly what you want:

The core property

Same bytes → same doc_key → same Firestore document → same chunk ids (tenant:sha256#i). Re-running the pipeline upserts the same rows instead of adding a second copy of every chunk beside the first.

Case 2 in detail: why the transaction is load-bearing

It is tempting to write the claim as "read the row; if it's empty, write it." That is a race with a window of a few milliseconds — and Pub/Sub delivers duplicates concurrently, so it is a window that gets hit in production.

Case 4 in detail: giving the claim back

A lock you can take but never release is worse than no lock at all. If a worker crashes between the claim and the finish, the row is stuck at processing forever — and every redelivery sees "already being handled" and does nothing. The document is then permanently missing, with nothing alerting, because from Pub/Sub's point of view every delivery was acked successfully.

So a failure writes status failed with the error text on the row, and the claim explicitly allows a failed row to be retaken:

retakes = ("failed", "superseded") if retake else ("failed",)
if snap.exists and snap.get("status") not in retakes:
    return False
A real bug this fixed

Without failed in that tuple, "give the claim back" gave nothing back. On the first live load, every retry of a failed document was acked as a duplicate and the document stayed failed forever.

The subtler kind: idempotent state, not just idempotent writes

Not writing a row twice is the easy half. The harder half is making sure that repeating an operation leaves the database in the same state. Three places where that took real care:

Ordering inside the swap

The swap flips new rows on before flipping old rows off. Run it again and it is a no-op — the new rows are already current and the old ones already have current: false, which the loop skips explicitly. Repeating the swap cannot produce a moment with zero visible versions.

Counting before the undo

The undo is only idempotent if the rows it expects still exist. So it counts surviving rows against the claim's recorded chunk count, and retired_at against the retention window. Refusing loudly (reactivate_incomplete, both numbers on the line) and changing nothing is the idempotent outcome — a partial flip is not.

The batch lane's second take

The long-document job takes its claim with the same transaction pattern: queued → processing, atomically. Two runs of the job can never index one document twice, and a document the job failed stays failed rather than being retried into a loop.

Where idempotency deliberately stops

Two things are intentionally not made repeatable, and knowing why is part of understanding the design.

  • A withdrawn source. When a person runs make retire, the tombstone holds against redelivery, against the nightly walk, and against the same bytes being uploaded again. "Repeat the upload and it comes back" would be idempotent — and wrong. A takedown is a decision, and only a person reverses it with make restore.
  • Firestore and the vector index are not one transaction. They cannot be; they are separate services. The design absorbs this by ordering the writes so the visible state is never wrong (new datapoints go up after the swap; on an undo the ids go back before the newer version is removed), and by having the nightly reconcile measure and report the drift rather than pretending it is impossible.

How it is proved, not asserted

Idempotency claims rot quietly. These are held by gates that run on every change:

The lifecycle checkThe tombstone is never re-ingested or reactivated; the verified undo refuses on a shortfall and on a closed window and flips nothing; the batch claim is taken atomically — all against a fake Firestore.

The eight questions to ask of any RAG index

If you are building something similar, this is the checklist — each one is a question a reviewer can ask, whatever the database.

  1. Can you name a source, a version and a chunk, and does the chunk identity survive an insertion above it?
  2. Is change detected by hash and generation, never by timestamp, with a late redelivery ignored?
  3. Does an edit of one paragraph embed one paragraph, and is the embedding model stamped on every row?
  4. Can a reader ever retrieve two versions of one source? If the write is not a swap, does the reader guard?
  5. Is anything deleted by a person or a cron job, or only by a declared retention policy?
  6. Does a scheduled reconcile run, emit a drift number, and alert when it stays non-zero?
  7. Does a document change go through the same gates as a code change?
  8. Are lifecycle events metrics with alerts, and is the cache keyed to the current versions?
