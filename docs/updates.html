How an update is handled

Someone re-uploads acme/hr_policy_2026.md with one clause changed. Same file name, new bytes. Here is everything that happens — and, at each step, which part of the database design makes it possible.

The rule the whole path follows

An update should cost what changed, be invisible until it is whole, be reversible for free, and leave a trail a person can read.

The eight steps

  1. Guard — is this event even current?

    Cloud Storage numbers every version of an object with a generation. The message carries one; the sources/ ledger remembers the one it indexed. If the incoming generation is older than the ledger's, this is a late redelivery of an old version — acting on it would make yesterday's policy live again. It is logged as ingest_stale_event and acked. Nothing is downloaded.

    Otherwise the bytes are fetched by that exact generation, never "whatever the file holds now". An event and its bytes are one version.

    structure used the generation field on the ledger row — a single read decides it.

  2. Claim — may I be the one to process this?

    The worker computes sha256 of the bytes, which gives it doc_key = tenant_sha256, and tries to write documents/{doc_key} inside a transaction:

    @firestore.transactional
def _claim(tx):
    snap = ref.get(transaction=tx)
    if snap.exists and snap.get("status") not in retakes:
        return False              # someone already has it
    tx.set(ref, {"status": "processing", ...})
    return True

    The transaction is the whole point. A read-then-write without one is a race with a window of milliseconds — and Pub/Sub delivers duplicates concurrently, so it is a window that gets hit. Two workers both read "absent", both write, and the document is ingested twice.

    A refused claim is not a failure. Depending on the existing status it means: already done (ack as duplicate), waiting for the batch lane (ack as queued), or this is an undo (jump to step 7).

    structure used a content-derived document id, so the same bytes always contend for the same row.

  3. Parse and chunk

    A PDF's pages are counted by pypdf before any OCR is paid for. Over 250 pages it is handed to the batch lane — ingest_batch/{doc_key} written, the claim set to queued, and a Cloud Run job with no request deadline picks it up. Everything else is parsed inline.

    Text is cut by section when it has ## headings, otherwise into 2,000-character windows with 200 characters of overlap, cut page by page so a window never crosses a page break. Every chunk gets its chunk_hash and a locator. One PII scan runs per document.

  4. Carry-over — pay only for what changed

    Before embedding anything, the worker reads the previous version's current rows for this source and builds a lookup of chunk_hash → vector. Then for each new chunk: if its hash is in that lookup, reuse the vector for free. Only the misses go to the embedding API.

    A vector is reused only when the model, the version, the task type (RETRIEVAL_DOCUMENT) and the vector's 768 dimensions all match today's configuration. An old or unstamped vector is re-embedded rather than trusted.

  5. Stage — write it, but keep it invisible

    The new chunk rows are written with current = false, staged = true and an expire_at one day out. No reader can see them. If the worker crashes right here, the TTL policy cleans up the half-written version by itself and the next delivery starts fresh.

    structure used the current flag as a visibility switch, and expire_at as an automatic janitor.

  6. Swap — flip the new on, flip the old off

    One pass, in a strict order, in batches of 400 writes:

    1. New rows first: current = true, and the stage marks cleared. A reader between the two halves finds the new version — never no version.
    2. Then the old rows: current = false, plus superseded_by, superseded_at, expire_at = now + 30 days, and effective_to if the new version declares a date.

    A document up to ~250 chunks flips in a single commit, so the change is atomic. A longer one takes two commits — and the reader's own guard covers that window: the retriever drops retired rows and then keeps only the newest version per source, so even mid-swap it cannot return two versions of one policy.

    After the swap, the vector index gets the new datapoints and loses the retired ids, and (where configured) the managed mirror stores are updated.

    Note what is not here

    No row is ever overwritten in place, and no row is deleted. A re-issue is new rows beside flagged ones. That is what makes the next step possible.

  7. The undo — re-uploading the old bytes costs nothing

    The update was wrong. Upload the previous file again. Its doc_key is the hash of those bytes, so the claim lands on a row whose status is superseded — the system recognises this as an undo rather than a new document.

    Its chunks are still in the database, just flagged. So the undo is: flip the flags back, put the ids back into the vector index, then retire the newer version in turn. Nothing is re-parsed, nothing is re-embedded.

    But it counts before it flips. Two checks:

    • Are all the rows still here? The surviving rows are counted against the chunk count recorded on the claim.
    • Is the window still open? retired_at is compared against the 30-day retention.

    A shortfall or a closed window logs reactivate_incomplete with both numbers, changes nothing, and the worker ingests the bytes as a fresh version instead. The carry-over still reuses every vector the newer version happens to hold.

    The bug this check exists for

    The first version of the undo flipped whatever rows remained and retired the newer version on the strength of it. After the retention window the TTL policy had already taken the rows — zero were flipped, the newer version was retired anyway, and the source was left with no current version at all.

    One thing the undo will not do: bring back a source a person deliberately withdrew. That is a tombstone (status: withdrawn), and only make restore lifts it — not a redelivery, not the nightly job, not the same bytes uploaded again.

  8. Record — leave a readable trail

    Three writes close the update:

    • documents/{doc_key} → indexed, with chunks, reused, embedded, generation.
    • sources/{tenant~name} → the ledger row: the new doc_key, generation, sha256, the counts, the effective date, the embedding stamp.
    • ledger/{tenant} → a fresh corpus fingerprint (the hash of all current doc_keys).

    Then one structured log line, ingest_ok, carrying all of it — which becomes a metric, which has an alert on it.

Why the fingerprint matters

Caches are the classic way a correct index still returns a stale answer. Here, the answer cache and the context cache each record the corpus_fingerprint they were built from. Every change to what is current recomputes that fingerprint. The API compares the two in a single read; when they differ it logs cache_stale and runs uncached until the corpus is re-packed.

The cache does not need to be told a document changed. It notices.

Deleting the file and make retire are deliberately different states. The first is storage absence, which the nightly walk repairs the moment the file is back. The second is a decision, which nothing repairs but a person.

The nightly reconcile

Events get lost. A push subscription can fail its retries; a notification can never fire. So the event path is the fast path, not the only path: a scheduled job walks the bucket against the ledger every night at 23:30 IST and plans an action per file — ok, reingest, retire, backfill, check_bytes, or leave-alone for withdrawn and queued documents.

It ends with one number: drift, how far the ledger stood from the bucket when it started. An alert fires if drift stays above zero for two nights. One night's drift is a lost event; two nights' drift is a lane nobody is reconciling.

Crucially, reconcile has no second ingestion path. To re-index something it rewrites the object onto itself, which fires a normal event and runs the exact same eight steps. There is one code path for updates, so there is one code path to get right.

A reindex is a release

make reindex runs the offline evaluation gate first. A changed document that breaks the golden question set is caught before anything is deployed, the same way a code change is. Then a live evaluation scoped to just the questions that cite that document runs against a candidate deployment.
