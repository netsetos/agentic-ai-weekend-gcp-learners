How the Firestore database is designed

Firestore stores documents (records) inside collections (folders). Every document has an id. Almost every good decision in this system comes from choosing those ids carefully — because in Firestore, writing to the same id twice is an update, and writing to a new id is a duplicate.

The three identities

Before the collections make sense, one distinction has to be clear. A "document" in the everyday sense — say hr_policy_2026.md — is actually three different things, and the database keeps three different records for it.

IdentityWhat it isIts idExample
Source The place a file lives. Stays the same across every re-issue. tenant~path (Firestore ids cannot contain /, so it becomes ~) acme~hr_policy_2026.md
Version One specific set of bytes. New bytes = new version. doc_key = tenant_sha256 acme_4b81f0…
Chunk One passage of text plus its embedding vector. tenant:sha256#index acme:4b81f0…#7
A real bug this fixed

Chunk ids used to be just sha256#index, with no tenant. Two customers uploading the same public Act wrote to the same Firestore ids, and the second ingest silently overwrote the first customer's rows with its own tenant_id. Adding the tenant prefix to the id made the collision impossible. See the long comment in deploy/services/ingest/contracts.py.

The collections

Four collections carry the document lifecycle. The rest support retrieval, tenancy and auditing.

The four that matter

sources/{tenant~path}

the ledger

One row per file path. Answers "which version is live right now?" It holds doc_key, the storage generation, sha256, how many chunks, how many vectors were reused vs. freshly embedded, the date the document declares itself effective from, and a status.

This is what a professional indexer calls a record manager, and it is the single record that makes re-issuing a document possible.

documents/{doc_key}

the claim

One row per version. It is written before any work starts, as a lock: "I am processing these bytes." Its status moves through processing → indexed, or to failed, queued, or superseded.

Because the id is a hash of the content, a second delivery of the same file hits the same row and is recognised as a repeat.

chunks/{tenant:sha#i}

the corpus

The actual searchable data: text, its 768-dimension embedding, source_uri, page_start, locator, chunk_hash, the embedding stamp, and the two flags the whole design turns on: current and staged.

ledger/{tenant}

the fingerprint

One row per tenant holding a short hash of all their current doc_keys. It changes whenever anything is indexed, retired or reactivated — and on nothing else. Caches compare against it and know instantly that they are stale.

The fields that do the work

On a chunk row, five fields carry the whole update story. Everything else is payload.

FieldPlain meaningWho writes it
current true = readers may see this row. false = retired; it stays in the database but is invisible to search. the swap, the undo
staged "Written but not switched on yet." A brand-new version lands staged and invisible. the writer, cleared by the swap
chunk_hash The hash of the passage's own text, with whitespace collapsed. This is the chunk's identity across versions — it is how the system knows "this paragraph did not change, reuse its vector." the chunker
expire_at A timestamp. Firestore's TTL policy deletes the row after it. Set only on retired and staged rows. the swap (now + 30 days), the staged write (now + 1 day)
doc_key Which version this chunk belongs to. Lets one query separate the new rows from the old ones. the writer
embedding_model,
embedding_version,
embedding_task_type		 What the vector was made with. A vector is only reused when all three match today's configuration — otherwise it is re-embedded rather than trusted. the writer
locator A human-readable address inside the document (NP-03, p7-1, preamble). Survives an insertion above it, which a page number does not. the chunker

Chunking by section, not by character count

This sounds like a detail and is actually the single biggest cost saver.

If you cut a document into fixed 2,000-character windows, inserting one line at the top shifts every window. Every chunk hash changes. You re-embed the entire document for a one-line edit. That is exactly what happened: a re-issued handbook reused none of its 92 windows.

So when a document has ## headings, it is cut by section instead — one chunk per clause, with the clause code as the locator. Now a one-clause edit changes one chunk hash. The same handbook reused 281 of its 283 chunks and embedded 2.

Why this belongs in a database page

Chunk boundaries decide how many chunk_hash values survive a re-issue, and chunk_hash is what the carry-over query joins on. The chunking rule and the schema are one design, not two. The same rule lives in deploy/shared/documind_corpus.py so the teaching notebooks mint byte-identical chunks to the production worker.

Indexes: what Firestore needs declared up front

Firestore refuses a query it has no index for. Every index this system needs is declared in Terraform (deploy/terraform/firestore_indexes.tf) rather than clicked into existence from an error link, so a fresh project works on the first try.

IndexServes
chunks: tenant_id + embedding (768-dim, flat) Nearest-neighbour search within one tenant.
chunks: tenant_id + current + embedding The same search, pre-filtered to live rows only — retired versions never even enter the candidate set.
chunks: six combinations of current + doc_type + kind Filtered search ("only contracts", "only figures") with and without the current filter.
graph_edges, graph_nodes: tenant_id + id field Each hop of the undirected graph walk.
members.email (collection-group) "Which tenants is this person a member of?" across all tenants at once.

One deliberate omission: the retire query uses only two equality filters (tenant_id and source_uri), which Firestore serves from its automatic single-field indexes. The hot path of an update needs no composite index at all.

The one thing allowed to delete

Nothing in the application code calls delete on a chunk. Not the worker, not the nightly job, not an operator command. Deletion is a declared policy:

resource "google_firestore_field" "chunks_expire_at" {
  collection = "chunks"
  field      = "expire_at"
  ttl_config {}
}

A retired row gets expire_at = now + RETENTION_DAYS (30 by default) and Google's platform removes it later. A staged row that nothing ever swapped in gets expire_at = now + 1 day and cleans itself up. That one number is both the audit window and the undo window — how long you can prove what the document used to say, and how long you can take a bad update back for free.
