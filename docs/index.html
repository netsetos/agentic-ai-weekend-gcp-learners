How DocuMind stores and updates documents

DocuMind is a RAG system. People upload documents; the system cuts them into chunks, turns each chunk into a vector, and stores everything in Firestore so questions can be answered with citations. These pages explain the database design and — the hard part — what happens when a document changes.

Written in plain language

No prior knowledge of Firestore is assumed. Every claim on these pages points at the file in this repository that implements it, so you can read the code straight after the explanation.

The problem in one paragraph

Uploading a document for the first time is easy. The trouble starts on the second upload. The same HR policy gets re-issued with one clause changed. A cloud message gets delivered twice. Two workers pick up the same file at the same moment. Someone uploads the wrong version and wants it undone. A naive system answers questions from two versions of the same policy at once, re-pays for embedding 283 chunks when only 2 changed, or loses the document entirely when a worker crashes halfway.

DocuMind's answer is a specific database design. Six ideas carry the whole thing:

1. Three identities

A source (the file path), a version (the hash of its bytes), and a chunk (the hash of its text). Each gets its own record. Most bugs come from confusing them.

2. Keys made from content

The id of a version is a hash of the bytes themselves. Upload the same file twice and you land on the same record — so the second upload can be recognised as a repeat instead of becoming a duplicate.

3. Nothing is overwritten

A new version is written beside the old one. The old rows are flagged current = false, never deleted. That makes the update reversible for free.

4. Visibility is a swap

New rows land invisible. One pass flips them on and flips the old ones off. A reader never sees two versions of a document at the same time.

5. Only a policy deletes

No person and no cron job deletes a row. A retired row is stamped with an expiry date and Firestore's own TTL policy removes it after the retention window (30 days by default).

6. Every step can be repeated

Cloud messaging delivers "at least once", which really means "sometimes twice". Every step here is written so that running it again changes nothing. That is idempotency.
